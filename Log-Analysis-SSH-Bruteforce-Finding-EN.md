# Log Analysis Finding — SSH Brute-Force Detection

**Category:** Blue Team / Log Analysis / Detection Engineering
**Environment:** Self-hosted Debian 13 VM (UTM), isolated lab network only
**Source:** `journalctl -u ssh` (systemd journal — Debian 13 does not ship `/var/log/auth.log` by default; authentication events live in the systemd journal instead of a traditional log file)

## Objective

Analyze the SSH authentication log to locate and confirm the exact moment an earlier Hydra brute-force exercise succeeded, and document a reusable, plain-language rule for distinguishing a brute-force attack from normal login activity using log evidence alone — without a SIEM.

## Scope & Authorization

Performed exclusively against a personally owned, isolated virtual machine with no production data or external network exposure, using logs generated by a prior self-authorized lab exercise (see the companion write-up, `SSH-Bruteforce-Detection-Lab.md`).

## Method

```bash
sudo journalctl -u ssh --no-pager | grep "Accepted"
```

This filters the full SSH service log down to only successful authentication events (`Accepted password ...`), across every system boot recorded in the journal.

## Key Evidence

| Timestamp | Event | Source | User |
|---|---|---|---|
| Sep 09 19:11:26 | Accepted password | `::1` (localhost, IPv6) | khulud |
| Sep 09 19:21:19 | Accepted password | `::1` | khulud |
| Sep 09 19:26:35 | Accepted password | `::1` | khulud |
| **Sep 17 12:34:14** | **Accepted password** | **127.0.0.1** (localhost, IPv4) | **testuser** |

Immediately preceding the successful login above, the log contained **9 consecutive `Failed password for testuser` entries within a 2-second window (12:34:15–12:34:16)**, each from a different source port — the fingerprint of an automated, parallel brute-force tool (Hydra), not a human retrying manually.

## Detection Rule (plain-language)

A login attempt pattern should be flagged as a probable brute-force attack when **all** of the following are observed together in the authentication log:

1. Multiple `Failed password` entries for the **same username**, from the **same source IP**, within a short time window (seconds, not minutes).
2. Each failed attempt uses a **different source port** — indicating separate automated connection attempts rather than one retried session.
3. The sequence is followed by either a sudden `Accepted password` (successful compromise) or a sustained string of failures with no legitimate login in between (failed attack).

Legitimate user logins (e.g., `khulud` above) are, by contrast, infrequent, widely spaced in time, and show no preceding failed-attempt cluster.

## Skills Demonstrated

- Navigating systemd's journal as the modern replacement for traditional `/var/log` files
- Filtering large log volumes to isolate security-relevant events (`grep` on `journalctl` output)
- Correlating a historical attack (Hydra) with its exact log signature after the fact
- Deriving a reusable detection rule directly from raw log evidence, without tooling

## GRC Relevance

- Maps directly to **Logging and Monitoring** controls (ISO 27001 Annex A.8.15/A.8.16) — this exercise demonstrates the manual log-review process that a SIEM would otherwise automate and alert on.
- Reinforces the **fail2ban** control implemented in the companion exercise: the threshold used there (`maxretry=3` within `findtime=600`) is directly justified by this real evidence of attack velocity (9 failures in ~2 seconds far exceeds any legitimate user's retry rate).
- Demonstrates the full detect → document → remediate cycle expected of a SOC/GRC-blended analyst.
